# MatrixChatBridge 多平台与多版本适配规划

简体中文 | [English](multi-platform-roadmap.en.md)

本文说明多个 Minecraft 服务端如何共同接入机器人后端，并规划 Paper/Leaf、
Fabric、Forge/NeoForge 及不同 Minecraft 版本的适配路线。

## 1. 多个服务端的部署结论

是的，每个 Minecraft 服务端都需要安装一个与其平台和版本匹配的插件端。

例如一台机器运行三个服务端：

```text
原版服（Leaf）    → 安装一个插件端 ─┐
生存服（Paper）   → 安装一个插件端 ─┼→ 同一个机器人后端 :8766
模组服（Fabric）  → 安装一个 Fabric 模组端 ─┘
```

`8766` 是机器人后端的统一 WebSocket 监听端口，不是某一台 Minecraft 服的
专属端口。多个插件端可以同时建立独立 WebSocket 连接，共同使用这个端口。

每台服依靠以下三项区分：

- 唯一 `server-id`；
- 独立的 256 位 token；
- 独立 WebSocket 连接。

同一 `server-id` 同时只允许一条有效连接。新连接会替换旧连接，因此不能给
两台不同服务器配置相同 ID。

同一台机器上的 Minecraft 游戏端口仍必须不同，例如 25565、25566、25567。
这些游戏端口与机器人后端的 8766 没有冲突。

### 同机部署示例

```yaml
# 原版服插件配置
bridge:
  url: "ws://127.0.0.1:8766/minecraft"
  server-id: "vanilla"
  server-name: "原版服"
  relay-group: "main"
  game-port: 25565
  token: "原版服独立token"
```

```yaml
# 生存服插件配置
bridge:
  url: "ws://127.0.0.1:8766/minecraft"
  server-id: "survival"
  server-name: "生存服"
  relay-group: "main"
  game-port: 25566
  token: "生存服独立token"
```

两台服的 `url` 相同，ID、token 和游戏端口不同。它们的 `relay-group` 都是
`main` 时，可以互相转发聊天。

机器人后端迁移到其他 VPS 后，所有插件端把相同 URL 改为：

```yaml
bridge:
  url: "wss://bridge.example.com/minecraft"
```

仍然不需要为每台服设置不同的桥接端口。具体网络配置参见
[跨 VPS 与多服务端部署指南](跨VPS与多服务端部署指南.md)。

## 2. 当前版本的支持范围

当前 0.4.9 插件端基于：

- Paper API 1.21.1；
- Java 21；
- Paper `AsyncChatEvent`；
- Bukkit 事件、命令和配置系统；
- Adventure Component/MiniMessage。

因此当前 JAR 的正式目标是 Paper 1.21.1 及兼容的 Paper 分支。Leaf 通常保持
Paper API 兼容，但仍应把实际使用的 Leaf 版本纳入测试。

当前 JAR 不能直接安装到：

- Fabric 服务端；
- Forge 或 NeoForge 服务端；
- 只实现 Spigot/Bukkit API、缺少 Paper API 的服务端；
- Java 或 API 代际明显不同的旧版 Minecraft 服务端。

Fabric/Forge 生态中应称为“服务端模组”，但在本项目架构中仍统一归类为
“插件端（前端）”。

## 3. 目标架构

规划将当前单模块拆成平台无关核心和平台适配器：

```text
matrix-bridge-protocol
└─ JSON 协议、消息类型、校验、全局消息 ID

matrix-bridge-core
├─ WebSocket/WSS 客户端
├─ 认证、重连、ACK、重试和去重
├─ 配置逻辑与能力协商
└─ 不引用 Bukkit、Fabric、Forge 或 Minecraft 类

matrix-bridge-platform-api
└─ 事件、玩家、命令、调度、广播、文本转换接口

platform-paper
platform-fabric
platform-forge
platform-neoforge
└─ 各平台的事件和生命周期适配
```

机器人后端继续只处理统一协议，不关心连接方使用 Paper、Fabric 还是 Forge。
不同插件端只负责把平台事件转换为相同的结构化消息。

核心层不应直接使用：

- `org.bukkit.*`；
- `net.minecraft.*`；
- Fabric/Forge/NeoForge Loader API；
- Paper 专有事件；
- 某个平台专属的文本 Component 类型。

## 4. 平台适配接口

建议平台层至少提供以下能力：

```text
PlatformAdapter
├─ platformName / platformVersion / minecraftVersion
├─ registerEventListeners()
├─ registerCommands()
├─ runOnServerThread(task)
├─ listOnlinePlayers()
├─ broadcastBridgeMessage(message)
├─ playerId / playerUuid
├─ serializeGameText / plainGameText
├─ readConfig / saveGeneratedToken
└─ logger
```

所有网络回调进入游戏 API 前必须切换到对应平台允许的服务器线程。平台适配层
负责线程边界，核心层不能假定 Bukkit 主线程模型适用于 Fabric/Forge。

为了兼容不同文本系统，核心协议保留 `plain` 文本作为必选字段；富文本 JSON、
颜色、点击事件等作为可选能力。这样旧版本或不支持 Adventure 的平台仍能正常
显示纯文本。

## 5. 后端能力协商

当前 hello 已上报插件版本、Minecraft 版本和服务端软件。后续建议扩展为：

```json
{
  "pluginVersion": "0.6.0",
  "minecraftVersion": "1.xx.x",
  "platform": "fabric",
  "platformVersion": "...",
  "serverSoftware": "Fabric",
  "capabilities": [
    "player_chat",
    "player_join",
    "player_quit",
    "player_death",
    "advancement",
    "rich_text",
    "online_players"
  ]
}
```

后端应按 `capabilities` 判断功能，而不是根据 Minecraft 版本字符串猜测。例如
某个平台没有稳定的成就事件时，可以不声明 `advancement`，其他聊天功能仍然
工作。

新增 hello 字段应保持向后兼容：v2 后端忽略未知字段，新后端也应接受未
声明 capabilities 的旧插件端，并使用保守默认值。

## 6. Paper、Spigot 与各版本规划

### Paper/Leaf/Purpur

第一优先级保留 Paper 适配器，因为当前功能已经在这一体系上实现。Leaf、Purpur
等 Paper 分支原则上共用 Paper 构建产物，但正式发布前必须分别进行启动、聊天、
死亡、进退服、成就和命令测试。

不建议承诺“一个 JAR 支持所有 Paper 版本”。聊天事件、Adventure API 和 Java
运行时要求会跨版本变化。可以按 API/Java 代际发布不同构建产物。

### Spigot/Bukkit

当前使用的 `AsyncChatEvent` 是 Paper API，Spigot 不能直接加载相关类。若需要
支持纯 Spigot，应增加独立的 Bukkit/Spigot 适配器，使用其可用聊天事件，并把
文本转换为统一消息模型。

### Java 版本边界

当前核心使用 Java 21，并使用 record 和 JDK WebSocket 客户端。适配旧版
Minecraft 时不能简单修改 `api-version`：

- 每个构建产物必须使用目标 Minecraft 支持的 Java 版本；
- 面向旧 Java 的核心不能包含由更高字节码版本编译的 class；
- 若支持非常旧的 Java，需要把 record 改为普通类，并替换或封装不兼容的网络
  API；
- 新旧构建仍可使用同一个 JSON 协议连接后端。

建议先覆盖仍使用现代 Java 的版本，再单独评估旧版支持成本，不让旧版限制整个
项目的实现。

## 7. Fabric 适配思路

Fabric 版本应建立独立 Loader 模块，主要工作包括：

- 使用 Fabric 服务端生命周期初始化和关闭核心连接；
- 注册玩家加入、退出、聊天、死亡及进度相关事件；
- 使用 Brigadier 注册 `/matrixbridge` 和 `/matrixbind`；
- 把 Minecraft Text 转换为纯文本及可选富文本；
- 使用服务端线程执行广播、在线列表和玩家消息；
- 在 Fabric 配置目录保存 URL、server-id、token 和路由组；
- 声明为服务端模组，不要求客户端安装。

若某个 Minecraft/Fabric API 版本没有稳定事件，应优先使用官方或 Fabric API
提供的回调；只有没有公共事件时才考虑 Mixin，并把 Mixin 限制在具体版本适配
模块内，避免污染核心。

建议先选择一个实际长期运行的 Fabric 版本做首个目标，不要同时打开过多版本
分支。

## 8. Forge 与 NeoForge 适配思路

Forge/NeoForge 使用各自的模组生命周期、事件总线和命令注册机制，建议拆成两个
适配模块，不通过大量反射强行合成一个 JAR。

主要工作包括：

- 在专用服务端启动和停止阶段创建/关闭桥接核心；
- 监听玩家登录、登出、聊天、死亡、进度/成就事件；
- 使用对应平台事件注册命令；
- 在服务器线程广播 Matrix 和跨服消息；
- 使用平台配置系统持久化配置和生成的 token；
- 确保服务端模组不引用客户端专属类。

Forge 与 NeoForge 在不同 Minecraft 代际的 API 和构建工具可能不同，应按目标
版本分别编译和测试。后端协议与身份绑定数据库无需因此分叉。

## 9. 聊天安全和事件一致性

跨平台适配必须维持当前防回环原则：

- 只把真实玩家聊天事件上传；
- 从机器人后端收到的消息只作为系统/广播消息显示；
- 不伪造玩家重新触发聊天事件；
- 每条消息保留全局 ID，最多中继一跳；
- 各平台插件端都缓存最近处理的消息 ID。

不同 Minecraft 版本对聊天签名、聊天预览和消息装饰的处理不同。适配器应尽量
观察最终允许发送的玩家消息，不修改签名内容；Matrix 和跨服消息应作为明确的
系统消息显示，不能冒充某个玩家的原生签名聊天。

各平台还要统一以下语义：

| 事件 | 统一要求 |
| --- | --- |
| 玩家聊天 | 已取消的消息不上传，命令不上传 |
| 加入/退出 | 使用实际玩家 ID，保留 UUID（如果平台可靠提供） |
| 死亡 | 优先使用服务端最终显示文本，至少提供纯文本 |
| 成就/进度 | 只转发会公开播报的事件，避免刷屏 |
| 在线列表 | 在服务器线程读取，并标明来源 server-id |
| 下行消息 | 广播显示，不重新进入玩家聊天监听器 |

## 10. 配置兼容策略

不同平台可以使用不同物理格式：

- Paper/Spigot：YAML；
- Fabric：JSON、JSON5 或 TOML；
- Forge/NeoForge：平台推荐的配置格式。

但逻辑配置键应保持一致：

```text
enabled
url
server-id
server-name
relay-group
game-port
token
连接超时、重连、待确认队列和事件开关
```

文档示例应标注平台，不能让用户把 Paper YAML 直接复制为 Forge 配置。token
生成命令在各平台保持相同用户体验，但由平台适配器写入相应配置文件。

## 11. 构建和发布方式

建议使用 Gradle 多项目构建，并为每个平台/版本生成独立产物：

```text
matrix-chat-bridge-paper-<mc版本>-<项目版本>.jar
matrix-chat-bridge-fabric-<mc版本>-<项目版本>.jar
matrix-chat-bridge-forge-<mc版本>-<项目版本>.jar
matrix-chat-bridge-neoforge-<mc版本>-<项目版本>.jar
```

不要发布一个包含所有 Loader 的“大一统 JAR”。不同平台会扫描入口类和依赖，
大一统 JAR 容易产生类缺失、依赖冲突和错误加载。

每个发布产物应附带：

- 支持的 Minecraft 版本范围；
- 平台与 Loader/API 版本范围；
- 所需 Java 版本；
- SHA-256；
- 配置升级说明；
- 已验证服务端列表；
- 已知缺失能力。

## 12. 测试规划

### 核心自动测试

- 协议编码、解码和版本兼容；
- WebSocket 鉴权、断线重连和 token 轮换；
- ACK、重试、去重和队列上限；
- 跨服排除来源和最多一跳；
- 提及、绑定及同名玩家消歧；
- capabilities 向前和向后兼容。

### 平台契约测试

每个适配器必须通过同一份行为测试：

- 加入、退出、聊天、死亡、成就；
- 命令不上传、取消的聊天不上传；
- Matrix 消息能在主线程安全显示；
- 在线列表正确；
- token 命令权限正确；
- `#help` 按普通成员、admin、owner 身份显示对应指令；
- 后端下行消息不会形成回环。

### 实机矩阵

每个宣称支持的平台和 Minecraft 版本都至少进行一次真实专用服务端测试。不能只
凭“能够编译”就标记支持。

建议维护支持表：

| 平台 | Minecraft 版本 | Java | 构建状态 | 实机测试 | 功能缺口 |
| --- | --- | --- | --- | --- | --- |
| Paper/Leaf | 1.21.1 | 21 | 已有 | 待持续验证 | 基线 |
| Fabric | 待选定 | 随目标版本 | 规划 | 未开始 | 待评估 |
| Forge | 待选定 | 随目标版本 | 规划 | 未开始 | 待评估 |
| NeoForge | 待选定 | 随目标版本 | 规划 | 未开始 | 待评估 |
| Spigot | 待选定 | 随目标版本 | 规划 | 未开始 | Paper 聊天事件需替换 |

## 13. 建议开发里程碑

### 阶段 A：稳定当前 Paper 版本

- 完成 0.4.x 的实际运行验证；
- 补足重连、队列和事件监听测试；
- 明确 Paper/Leaf 的实际兼容版本；
- 建立统一支持矩阵。

### 阶段 B：抽离平台无关核心

- 建立 protocol、core、platform-api 和 paper 模块；
- 保证现有 Paper 功能与配置不回退；
- hello 增加 platform 和 capabilities；
- 后端根据能力工作，不硬编码平台。

这一阶段是后续所有平台的前置工作，建议作为 0.5.0 的主要目标。

### 阶段 C：Fabric 首版

- 先支持一个实际需要的 Fabric/Minecraft 版本；
- 完成聊天、进退服、死亡、绑定、在线列表和下行广播；
- 成就与富文本可根据平台能力逐步补齐；
- 通过与 Paper 服互相中继的端到端测试。

### 阶段 D：Forge/NeoForge 首版

- 根据实际模组服版本决定先做 Forge 还是 NeoForge；
- 复用 core，只开发事件、命令、线程、文本和配置适配；
- 分别发布对应 Loader 的 JAR；
- 与 Paper/Fabric 进行混合跨服测试。

### 阶段 E：旧版和代理层

- 根据真实用户需求选择旧版 Paper/Spigot，而不是一次支持全部历史版本；
- 单独处理旧 Java、旧聊天 API 和旧文本格式；
- 评估 Velocity/BungeeCord 适配器，用于代理层公告或全网在线信息；
- 不让旧版兼容代码降低现代平台的安全性和可维护性。

## 14. 推荐优先级

建议按以下顺序投入：

1. 当前 Paper/Leaf 1.21.1 稳定运行；
2. 抽离 core 和 Paper adapter；
3. 选择实际正在使用的 Fabric 版本；
4. 选择实际正在使用的 Forge 或 NeoForge 版本；
5. 再根据用户数量决定旧版 Spigot/Paper；
6. 最后评估代理端和普通 HTTPS 传输。

最关键的决策不是“理论上支持多少版本”，而是先确定首批真实目标版本。每增加
一个 Minecraft 版本和 Loader 组合，都会增加构建、测试和故障支持成本。
